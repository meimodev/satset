## Project

SatSet — Flutter 3.41+ Android-only (minSdk 29) LAN restaurant ordering app. Single APK runs in **Server** or **Client** mode, paired over Wi-Fi via mDNS auto-claim.

Stack: `flutter_riverpod`, `go_router`, `intl`, `uuid`, `freezed`, `json_serializable`, `drift`, `shelf` (+ `shelf_router`, `shelf_web_socket`), `web_socket_channel`, `http`, `flutter_secure_storage`, `shared_preferences`, `bonsoir` (mDNS), `basic_utils` + `dart_jsonwebtoken` + `crypto` (TLS / JWT).

### Codegen scope

`build_runner` (`freezed`, `json_serializable`, `drift_dev`) only runs under:

- `lib/data/models/**` — wire DTOs
- `lib/domain/models/**` — domain models (selective; some are plain Dart)
- `lib/server/db/**` — Drift schema + DAOs
- `lib/data/db/**` — the **client** Drift DB (ADR-0124): the [[Antrean setelmen]], cached bills, and the [[Salinan pelanggan]] (ADR-0129). No `drift_schemas/` harness on this side — its `onUpgrade` is hand-written and guarded by `test/client_db_migration_test.dart`

Generated `*.g.dart`, `*.freezed.dart`, Drift outputs excluded from analyzer. Run `tool/codegen.sh` (= `dart run build_runner build --release`) after editing those.

Localization is a **separate generator**, not part of `build_runner`: `lib/l10n/*.arb` → `flutter gen-l10n` → `lib/l10n/app_localizations*.dart`, configured by `l10n.yaml`. Output is committed and analyzer-excluded, so tests and CI need no generate step.

UI, repositories, services, server routes, use cases: hand-written.

## Architecture

Three layers pointing one way: `ui/` ← `domain/` ← `data/`. Server lives separately under `server/`.

Enforced by `test/layering_test.dart`, which bans each cross-layer import and carries a **frozen allowlist** of the four files that already break it (ADR-0104) — the three use cases, which import `flutter_riverpod` and reach down into `data/repositories/`, and `data/services/alert_sound_service`, which reaches up into a `ui/` view model. Entries come off that list when an import goes away; nothing goes on. `lib/domain/models/**` is pure with no exceptions.

**Entry:** `lib/main.dart` → `ProviderScope` → `SatSetApp` (`lib/app.dart`) → `MaterialApp.router` wired to `routerProvider`.

**`lib/server/`** — embedded shelf server (runs in-process in Server mode).
- `server.dart` — bootstrap, mounts router, runs TLS listener.
- `routes/` — `auth_routes`, `tables_routes`, `tickets_routes`, `menu_routes`, `reference_routes`, `health_routes`, `cash_routes`, `members_routes`, `self_order_routes`.
- `db/` — Drift: `database.dart`, `tables.dart` (schema), `seed.dart` + `seed_data.dart` (DB seeded on first boot — no more `DummyData`), `seed_history.dart` + `seed_history_mix.dart` (the fabricated month), `seed_inventory_data.dart` (bahan + resep).
- `seed_job.dart` — job marker + the venue-wide "prompt answered" flag (ADR-0073).
- `audit_log.dart` — **the** audit writer (`writeAudit`) + wire shape (`auditJson`). Every route that audits an act goes through it; hand-rolling the insert is how a new column reaches three call sites out of four. A row stores an `AuditKind` + params, never a sentence (ADR-0085) — the words are composed at read time by `auditText` in `lib/core/localization/audit_text.dart`.
- `cash.dart` — **the** petty cash writer (§Kas kecil). Every write to `cash_entries` goes through it, for the same reason `writeAudit` exists. Holds the two invariants: the balance is always `SUM(delta)` (nothing stores it) and the box cannot go negative (ADR-0088, with a reversal and a count exempt). `cashReportSection` is the Kas report block — a count's delta is booked as variance, never as cash moving (ADR-0089).
- `members.dart` — **the** membership writer (ADR-0091…0095), third of the same family. Holds the invariants: a points balance is `SUM(delta)` and never stored, never negative, never expires (ADR-0095); a member is identified by phone, so a merge folds one record into another and a delete anonymises rather than erases (ADR-0092). Points are earned once, at bill close, and reversed by a `MemberPointKind.reversal` row if the bill reopens — nothing is ever edited in place. `memberReportSection` is the Keanggotaan report block, and `memberTradeReport` / `memberHistory` are the Laporan pelanggan report (ADR-0119) — which hands the section its already-walked scans so the tiles and the list cannot disagree about the same split bill.
- `stock_counts.dart` — **the** stok opname writer (ADR-0096), fourth of the same family. An opname is a *session*: `stock_counts` header + `stock_count_lines`, opened, walked, then closed. Nothing moves until `closeCount`, which writes the `adjust` movements — each stamped with its `countId` — and exactly one `AuditKind.stockCountClosed` row. A line freezes its expectation at first entry, so a sale during the walk lands in the ledger and never in the variance; a zero-variance line is kept, because "counted and matched" is a finding. `recordCount` on `stock.dart` is gone — there is one path.
- `self_order.dart` — **the** pesan mandiri writer (ADR-0105), fifth of the same family. Holds three invariants: a guest order is an **intent** (`guest_orders` + `guest_order_lines`), never a ticket, so no reader of `tickets` can see it before a human accepts it; the guest is untrusted, so **the server prices the order** from `menu_items` and a `unitPrice` on the wire is ignored; a decision is **once** (`_claim` re-reads `status` inside `db.transaction`). `acceptGuestOrder` calls the ordinary `submitOrder`, which is the whole point — there is one path that writes a ticket.
- `guest/` — the **cleartext plane**, boundary as a directory: `guest_plane.dart` (a second `shelf_io.serve` on :8080, no `securityContext`, bound only while the venue flag is on), `guest_routes.dart` (takes **no `ServerAuth`** — deliberately outside ADR-0102's contract, because the way to keep a stranger out of the staff API is a router that never heard of it), `guest_code.dart` (the 8-char alphabet, split out to break a `database.dart` ↔ `self_order.dart` import cycle). The page itself is `assets/guest_web/index.html`.
- `auth.dart` (PIN + JWT), `tls.dart` (self-signed cert), `mdns.dart` (advertise), `ws_hub.dart` (WebSocket broadcast). Pairing is a single unauthenticated `POST /pair/auto-claim` in `server.dart` that upserts the `Devices` row; there is no token table (ADR-0080).

**`lib/core/log/`** — `sat_log.dart` (logger), `sat_nav_observer.dart` (router observer).

Widget book: every `core/widgets/` widget in all its states against stub data, with theme/skin, text-scale, reduced-motion and phone/tablet toggles. In the pair-gate bypass set, so it works unpaired. Two entries: a debug button on `PinScreen` (pre-pairing) and a "Book" item at the foot of `TabletSideRail` (pushed, not `go`ne — back returns to your tab). Lives in `lib/ui/features/_book/`.   - `AppShell` is also the app's **only** error-bus subscriber (ADR-0103) — a repository pushing to `errorBusServiceProvider` surfaces as a snackbar here, from whatever screen the user has since walked to.
  - `/alerts` = alert config (thresholds + sounds + this-device mute), reached from the Venue hub. Gated `editSettings`.
  - `/audit` = venue-wide integrity log (ADR-0072), reached from the Venue hub. Gated `viewReports`; admin rows need `manageStaff` on top, enforced server-side. **Tablet only** — the phone route renders an explanation. A row with a non-null `paymentId` shows a camera glyph and opens the proof photo on tap (ADR-0086) — this is the only place proofs are browsed across a range; Reports has no payments section.
  - `/members` = the Pelanggan (member) directory (ADR-0092), reached from the Venue hub. Gated `manageMembers`. **Tablet only**, like `/audit` and `/kas`. Reading a member is open to the till server-side, but the till reaches one through the bill overlay (`ui/features/cashier/member_panel.dart`) — this route is where records change. Enrol / edit / adjust points / merge / delete all live here; nothing on this screen touches a bill.
  - `/member-report` = the Laporan pelanggan report (ADR-0119), reached from the Venue hub. Opened by `viewReports` **or** `manageMembers` — the `/kas` and `/opname` list shape. **Tablet only.** Two panes: the ranked list of everyone who traded in the window on the left, one member's bills and product rollup on the right. The list is capped server-side at 500 and **sorted and filtered client-side**, so no sort costs a round trip. Its range chips are `MemberRange`, deliberately **not** `ReportRange` — it carries an open-ended `Semua` arm that `/reports` must never be offered, because that payload is per bill and this one is aggregated. Read-only, and the Keanggotaan block on `/reports` is untouched.
  - `/opname` = the stok opname archive (ADR-0096), reached from the Venue hub. Opened by `viewReports` **or** `manageIngredients` — the list shape `/kas` uses, because the person who counts and the person who reads the variance back are rarely the same. **Tablet only.** Read-only: counting happens on `/stock`, and this is where the closed sessions are filed. Export (PDF filing copy / CSV) is built client-side from the loaded document — a session has no paging, unlike the venue log.
  - `/selforder` = the **[[Tamu]] queue** (ADR-0105, ADR-0106) — where a waiting guest order is accepted or rejected. A **top-level nav destination on both form factors**, not a hub child: the Venue hub is `manageStaff`, so as a hub child it was unreachable on a tablet by the very role it is for. Rail id `tamu`; the slot appears only when `guestOrderingEnabled && has(takeOrder)` (`showGuestQueue` in `app_shell.dart`), badged with the pending count. Route still opens to `takeOrder` **or** `editSettings`, because the server hands an owner the queue read too.
  - `/selforder-admin` = **Pesan mandiri** configuration (ADR-0106) — QR & meja / Menu tamu / Aturan, including the master on/off switch. `editSettings`, **tablet only**, reached from the Venue hub tile (whose badge is on/off, not a backlog). Must be matched **before** `/selforder` in `_capabilityFor` — one path is a prefix of the other. This is the staff half; the guest half is a different socket entirely.
  - `/kas` = the petty cash box (§Kas kecil), reached from the Venue hub. **Two capabilities open it** — `manageCash` (post an expense) or `editSettings` (fund it, count it) — which is why `_capabilityFor` returns a *list* and any one of them is enough; which of the three actions each may take is enforced per-route, server-side. **Tablet only**, like `/audit`. Nothing here is revenue (ADR-0089) — the box is not the cash drawer, and `openDrawer`/`closeShift` stay reserved for the drawer.
- **Outside the shell** (root-navigator pushes, full-page transitions):
  - `/table/:id` (+ `/menu`, `/review`, `/sent` subroutes) — order-taking flow.
  - `/menuadm/:id` — menu item editor.

**Redirect guard order:**
1. Hard pair gate: `apiConfigProvider == null` → `/pin` (no data screen renders against an empty repo cache).
2. Not authenticated → `/pin`.
3. Authenticated on `/pin` → `/venue` (server mode) or `/tables` (client mode), per `prefs.appMode()`.
4. Authenticated elsewhere → `_capabilityFor(loc)` returns the capabilities that open it; **any one** is enough (`needed.any(auth.has)`); fail-closed → `/forbidden`.

Capabilities (`domain/models/capability.dart`): `viewKds`, `takeOrder`, `manageStaff`, `manageCash`, … Route → capability mapping is in `_capabilityFor` at the top of `app_router.dart`, and each arm must mirror the capability the **server** demands of the writes that screen makes — the client gate decides what to offer, never what to allow.

A **ticket transition** carries its capability in the graph itself: `ticketTransitions` in `lib/domain/models/ticket_transitions.dart` maps `from → to → Capability`, and both the client use case and the server route read that one table (ADR-0101). A move's presence is what makes it legal; there is no separate "which capability does this cost" switch to forget an arm in. A move nothing writes gets no row — `draft → sent`, `acknowledged → prep` and `sent → held` were legal, writerless and therefore ungated, which is the whole failure mode. The statuses stay (they are persisted strings, reserved on purpose); the arms come back the day a writer does.

### Shell

`AppShell` (`lib/ui/features/shell/app_shell.dart`) picks tablet (`TabletShell`) vs phone (custom `Scaffold` with `SatAppBar` + floating tab bar) based on `context.layout.useTabletShell` — hardware decides, there is no runtime override (ADR-0049 removed `forcePhoneViewProvider`). ## Gotchas

- Don't name a class `Table` — conflicts with `dart:ffi`. Use `VenueTable`.
- Portrait + tablet layouts both rendered — check `tablet_chrome.dart` when adding shell-level UI.
- `.codegraph/` and `graphify-out/` lag a beat behind file writes.
- DB is the source of truth in Server mode; seed via `lib/server/db/seed.dart`, not via in-memory `DummyData` (gone).
- **One seed, not two** (ADR-0073). `seedSampleVenue` = reference half (4 zones / 20 tables / ~42 items / 4 staff — 2 waiters + 2 kitchen / bahan+resep) **plus** a fabricated month of ~1500 bills and its audit trail, written through the production order path. It refuses on a venue that has traded; `clearSampleData` deletes the `contoh-` tagged transactional rows only, leaving the menu standing. The old demo seed and demo clock are gone — a seeded venue runs on real time, and backdating goes through the `at`/`idPrefix` overrides on `submitOrder`, `receiveStock` and `writeAudit`. A new seeded menu item needs a resep, bahan and a weight in `seed_history_mix.dart` or the seed will reject its lines for want of stock.
- The first-run seed prompt is a **blocking, non-dismissible dialog** on the Venue Hub, answered once and recorded server-side. Admin → Sistem → Operasional holds the permanent way back in.
- `apiConfigProvider == null` blocks every non-onboarding route — pair before exercising data screens.
- **Never rename an `AuditKind`** (`lib/domain/models/audit_kind.dart`). The name is persisted in `audit_entries.kind` and is the join to the ARB template; a rename silently drops every existing row back to its frozen Indonesian `title`. Adding one means an ARB entry in both locales — the `switch` in `auditText` is exhaustive, so the analyzer will say so.
- **`CashEntryKind` names are persisted** in `cash_entries.kind`. Renaming an enum value orphans every existing row — the resolver falls through to the raw key, so it fails silently as a code where a word should be. Adding one needs an ARB entry in both locales.
- **A category is the venue's word, and the box owns it** (ADR-0135, amends 0131 and reverses 0130's closed-set half). `CashCategory` stopped being an enum: `cash_categories` is keyed **`(box_id, id)`**, so Kas Dapur lists what a kitchen tin buys and the bar tin lists its own, and the five stock slugs (`ingredients`, `operations`, `transport`, `dailyWage`, `other` — the names the enum persisted) are seeded into **every** box on create, on the v75 upgrade and on every Server boot. That composite key is the whole migration: **nothing backfills `cash_entries`**, because a pre-v75 row resolves against the `box_id` it already carries. The five stock words therefore **left the ARB** and are venue content now, renameable. A rename is **retroactive** — the entry stores the id and the word resolves on read, `VisitExpenses`' posture and not `Discounts`' — with one deliberate asymmetry: `auditParams['category']` writes the word at movement time, so `/audit` keeps the original while `/reports` shows the new one. `spendCash` validates the category **against this box** inside the write transaction beside the ADR-0088 balance check (ADR-0100); another tin's id is `unknown_category`. Authoring is `editSettings` on `/kas` and writes **no audit row** — a box audits because it holds a balance, a category is vocabulary — riding the existing `cash.boxes` WS frame, which now carries `{box?, boxes, categories}`. The report's venue-wide `byCategory` is keyed by **the venue's own word**, not a code, so two tins that both authored *Sayur* read as one line; each `byBox` entry carries its own, keyed the same way. There is **no guard against retiring the last category**: the sheet shows an empty state and the write path still refuses `category_required`.
- **A kas export is a fresh window, and the balance is not in it** (ADR-0136). `/kas` carries a [[Jendela kas]] — `GET /cash` takes `from`/`to`, both absent being the **Semua** arm the screen opens on — and the window narrows the *list*, never the balance: a box's balance stays `SUM(delta)` over all time (ADR-0088), because a windowed one reconciles against nothing anybody can count. What a window produces instead is **movement**, and the **server sums it** (`cashWindowTotals`, beside `balance` in the response) over every row in the window regardless of `limit`, because the list is paged and a client summing what it holds sums the pages someone happened to scroll; a count's delta books to `variance` and never to outflow, the one rule this shares with `cashReportSection`. Export is `limit=all` — unpaged, capped at `kCashWindowMax` (5000) and **refusing `window_too_large` rather than truncating**, since a short ledger that looks complete costs a reconciliation while narrowing costs one tap. Both formats render **client-side** from that one payload (`lib/core/export/cash_exporter.dart`), departing from `/audit/venue.csv`'s server-rendered posture *because* of the PDF: a server CSV plus a client PDF is two renderers of one ledger that will disagree about a retired category or a transfer's other leg. A renamed [[Kategori kas (cash category)]] prints its **current** word — this is an export of `/kas`, and `/audit`'s frozen word stays `/audit`'s (ADR-0135). No running-balance column (order-dependent, and a spreadsheet gets re-sorted); reversals and both transfer legs are in, with linkage. Proof **photos ride the PDF and only the PDF** — a documented exception to `cash_routes.dart`'s "blob never rides the ledger path", bounded by being opt-in, fetched one at a time through the existing per-row route, downscaled to 700px q70 off the UI isolate and capped at `kCashPhotoMax` (60) with the footer counting what was left out; a failed fetch is a placeholder plate, never an aborted export. A live WS row is admitted only when the window's top is open (`CashWindow.admits`) and admitting one triggers a re-read, because the totals are the server's to sum. Exporting writes **no audit row** — a read is not a movement.
- **A section that renders on `/reports` must reach its export.** For four releases the screen drew Kas, [[Pengeluaran kunjungan]], [[Piutang]] and Jam kerja while `reports_exporter.dart` wrote none of them — nothing failed, the blocks were simply absent from the CSV and the PDF an owner filed, including the two ledgers an accountant is most likely to be after. `test/reports_export_sections_test.dart` is the guard and it works structurally: it reads `l10n.rptSec*` out of `report_sections_view.dart` and fails when the exporter never names that section's snapshot field, so a **new section needs its `fieldFor` entry and its export in the same commit**. `rptSecBahan` is the one exemption — stock comes from its own provider, not the snapshot, and has its own export. A block whose window is empty is left **out** rather than written blank: an empty section in a filing copy reads as a failed fetch, not as a quiet box.
- **An export is a fresh uncapped fetch, not what the screen is holding** (ADR-0137). Every membership read is server-capped — the directory and the ranked list at 500, a member's bills at 200 — and those caps are invisible on a screen that scrolls but load-bearing in a **file**, which has a name and gets filed. So the three membership exports (`/members/export`, `/members/report/export`, `/members/<id>/report/export`) re-ask with the cap lifted and return **JSON the client renders**, the `/reports/staff` shape and not `/audit/venue.csv`'s — the server carries no `package:pdf`. Lifting the existing `limit` instead is the trap: the clamps are `.clamp(1, 500)`, so a client asking for 100000 gets 500 and a `200 OK`. "Uncapped" is bounded by `kMemberExportMax` (20000) and crossing it **refuses loudly** (`413 export_too_large`, naming the limit) — a silent stop at row 500 is the whole failure. `membersTruncated` is stripped from the export payload, because on an uncapped answer it can only ever say zero. They gate **what their screen gates and nothing more**: §Export's `viewReports`-for-everything rule exists because the *order board* is open to `takeOrder`, and here a `manageMembers` holder already reads every figure on screen. The directory export is the one that *narrows* — `manageMembers` alone, unlike `GET /members`, which the till and the booking form also read — which is also what keeps a masked `takeOrder` device (ADR-0129) away from an unmasked file; there is no masked export. **The file is the screen**: the directory carries its search/birthday/lapsed filters and names them in the header, the ranked list carries the search box and the active `MemberSort` through `rankedMemberRows` (hoisted off the screen so a second filter-then-sort cannot drift). **One** export audits itself — `AuditKind.memberDirectoryExported` on `AuditType.memberChanged`, because the roster is names, numbers, birthdays and addresses leaving through the share sheet; the two report exports are aggregates their reader already had on screen and write nothing. Its own sheet on `/member-report`, never a fifth `Jenis` on the Reports one: that sheet reads `ReportRange` and this screen runs on `MemberRange`, whose `Semua` arm the accounting export must never be offered. Host dark ⇒ **refuse in those words**, never export the [[Salinan pelanggan]] (maskable, and holds no window aggregates). Kind slugs live in `member_exporter.dart` as `MemberExportKind`, not in `lib/ui` — `design_tokens_test.dart` reads an Indonesian word in a Dart literal there as copy that skipped the ARB.
- **`MemberPointKind` names are persisted** in `member_points.kind`, same rule as above.
- **`StockCountScope` names are persisted** in `stock_counts.scope`, same rule again. And `stock_movements.count_id` is nullable *by design* — an `adjust` written before v52 predates the session concept and is deliberately not backfilled (ADR-0096), so anything reading it must treat null as "pre-session", never as an error.
- **Bumping `schemaVersion` means dumping the schema.** `drift_schemas/` holds one JSON per version and `test/schema_migration_test.dart` migrates the oldest forward, comparing the result against what Dart declares. Bump the version without dumping and that test fails asking for the dump:

  ```bash
  dart run drift_dev schema dump lib/server/db/database.dart drift_schemas/
  dart run drift_dev schema generate drift_schemas/ test/generated/schema/
  ```

  Output is committed and analyzer-excluded, like the other generators. **A new `venue_settings` column must also be listed in the v63 rebuild's `newColumns`** — that branch copies the *declared* schema through `TableMigration`, so a column it has never heard of is selected out of a table that predates it, failing the upgrade rather than just the test. The harness is what caught v63: two guest-ordering flags and `sound_guest_pending` had reached upgraded venues without the `CHECK` / `DEFAULT` clauses a fresh install gets, because `_safeAddColumnOn` takes a raw type string and nothing compared the two populations.
- **A migration branch is gated on both ends** — `if (from < N && to >= N)`. In production `to` is always `schemaVersion`, so the upper bound never changes what runs; it exists so a test can replay one branch at a time. Without it, a fixture for an early transform has to survive every later branch, including the v27 one that deliberately wipes transactional data, and no assertion survives that.
- **A [[Modul]] is an entitlement, and a feature needs both halves** (ADR-0107). The cloud owns `venues/{id}.addOns`; it mirrors down to `venue_settings.modules` as a CSV, and `hasModule` is what every *sellable* gate asks — a **mode** key is a different question and reads its absence the other way round (ADR-0109, next bullet). The plan **never enters `hasModule`** (ADR-0108): a trial holds exactly what its `addOns` says, same as a partner — a trial is *created* holding every module, but that is a provisioning default an operator can untick, not a read rule. `modules` **NULL means never mirrored and reads as entitled**, which is the fail-open a LAN venue that has not phoned home depends on; `''` is the different, real answer "holds no module". Server-side the entitlement ANDs with the owner's own switch (`membersEnabled`, `guestOrderingEnabled`) and an unentitled route answers **404**, same as never opting in. Client-side that AND lives in **one** place — `VenueSettingsModules` on the settings DTO (`membersOn`, `guestOrderingOn`, `lib/data/models/venue_settings_dto.dart`) — and every floor surface reads those, never the bare preference; gating on the preference alone leaves an unentitled venue a button whose only outcome is that 404. Removing a module **freezes, never deletes**: the preference stays stored and comes back on re-entitlement. The console refuses to remove `members` while member debt is outstanding.
- **Counter mode is a preset of switches, and its key fails closed** (ADR-0109, amends 0107). `counterService` is a **mode** key, not a sellable one, so it deliberately does *not* go through `venueHasModule`. `lib/server/modules.dart` carries two resolvers and merging them is the failure: `venueHasModule` fails **open** (`modules == null` reads as entitled — the fail-open a LAN venue that never phoned home depends on), `venueHasMode` fails **closed** (absent, null and unmirrored all read as off), and `counterSwitchOn` ANDs the mode key with the per-switch CSV. Client-side the same pair is `counterMode` / `counterOn(key)` on the **same** `VenueSettingsModules` extension that carries `membersOn` — one place, like the sellable half. Fail-open applied to a mode would boot every not-yet-mirrored *restaurant* as a counter shop with its floor hidden, which is the whole reason there are two functions. The six switches — `menuHome`, `anonTakeaway`, `settleAfterSend`, `simpleKds`, `counterQr`, `ringkasReport` — live in `venues/{vid}.counterConfig`, mirror to `venue_settings.counterConfig` as a CSV, and are **persisted strings** under the same never-rename rule as `AuditKind`. They are config, not entitlement, so an eighth switch costs a map entry and not an unrenameable key. The preset is a **write, never a read**: ticking `counterService` on the console turns all six on and the operator unticks from there — nothing computes "is this venue in the preset", which is what keeps "cafe with a small floor" expressible instead of a rung between two tiers. Every switch is a *default or a layout*, **never a branch in a writer** — a switch that changed what `submitOrder` writes is a review finding, and the only server-side read is `counterGuestCode` (`lib/server/self_order.dart`) gating whether the [[Kode kedai]] socket route *exists*, exactly as `guestOrderingEnabled` does. That ban is on a **switch**; a **mode key** may branch a writer, and exactly one does (ADR-0115, next bullet). Counter mode **hides, never refuses** (ADR-0109 §6): tables, zones, reservations and locks stay legal server-side and keep being written, so a cafe that adds four seats unticks `menuHome` and finds everything where it was. A fleet toggle reaches the floor on the venue's next admin sign-in; `counterQr`, being a socket route, needs a server **restart**.

- **A venue may have no prep queue, and that is a second mode key** (ADR-0115, amends 0109). `bypassKds` sits beside `counterService` in `venueModeKeys` / `MODE_MODULES` — fail-closed through `venueHasMode`, outside the trial grant — and is **independent of counter mode**: it is deliberately *not* a seventh `counterConfig` switch, because a counter shop may still run a cook line and a small restaurant may have none. It is the **one** key that branches a writer: `submitOrder` writes `ready` with `readyAt` stamped at send instead of `sent`, read from the venue's own settings row rather than the wire, so `acceptGuestOrder` and an [[Antrean kirim]] replay inherit it with no second arm. **`ready`, not `served`**, and the transition graph is the reason — `ready → voided` costs `voidItem`, `served → voided` costs `compItem`, so a born-`served` line would need a manager to void a mis-key in the one-person shop that has none; `ready → served` is already the handover tap on `/orders`, so the board needs no new UI. Everything else **hides and nothing is revoked**: the KDS rail slot, the prep metrics in Operasional, `prepTargetMins`, the prep-queue cues (`newOrder`/`overdue`/`orderReady`) and the `viewKds` row in the role sheet all go, while the stored capability, threshold and `simpleKds` value stay put — `setCapability` rebuilds its PATCH from the *stored* role, never from what the sheet renders, which is why hiding a row cannot drop a capability. Two survivals keep the hiding honest: the KDS slot returns while any line is still `sent`/`prep`/`cooked` (`kitchenQueueLiveProvider` — flipping the mode on mid-shift drains rather than strands) and for a `viewKds`-only signed-in user. The **route is never gated** — 0109 §6 holds for the route; what this amends is only what gets written. The venue **shape is cached** in `PrefsService` and re-read at `VenueSettingsRepository` construction, because a mode fails closed and a cold-boot-offline handset would otherwise render a KDS tab and a floor the venue does not have; that fixes `menuHome` too. **Widened by ADR-0128** to the whole settings DTO — see the next bullet; `venueShape()` is now `legacyVenueShape()`, read once on the upgrade boot and never written.

- **A client caches the venue's settings whole, and stale beats absent** (ADR-0128, amends 0115). Every field on `VenueSettingsDto` fails closed through its freezed default, so caching only `modules` + `counterConfig` left a cold-boot-offline device rendering a venue with **membership off, guest ordering off and every threshold at the factory number** — `MemberPanel` returns `SizedBox.shrink()` on `!cfg.membersOn`, so the panel did not degrade, it *vanished*, on the screen where money is taken. The whole payload now goes to prefs under `satset.venue_settings` and is painted into `state` **in the constructor**, not the bootstrap microtask — a widget's first build reads state before any microtask runs, and the first frame is the one that was wrong. `_adopt` is the only path from payload to state; a site that assigns `state` directly leaves the cache a version behind. The cache **dies with the certificate, not the address** — ADR-0080's rule, and 0128 got it wrong first: keying on host:port meant `relocateServer` destroyed a venue's own settings on every DHCP turnover, exactly when the device could not reach its host. The blobs are stamped with the fingerprint they came from (`satset.venue_cache_fp`) and dropped only when a config names a different one; the check runs when a config **arrives**, not at read time, because the constructor paints before any fingerprint is knowable — sound because a device cannot re-pair while offline. Dropping resets `state` too, not just prefs, since the foreign venue is already painted. An unstamped cache reads as *unknown*, never *foreign*. The [[Preset diskon]] catalogue caches the same way and is **warmed on `AppShell`** beside `sendQueueDrainProvider` — its repository is lazy, so the first watch used to be the cashier opening the discount sheet, and on a dark handset that fetch failed and the sheet said the owner authored no presets. The member **directory is deliberately not cached** (ADR-0123 stands, the phone is the identity): the lookup sheet renders offline / loading / empty as three visibly different states and withdraws enrolment rather than offering a write with nowhere to land. Two older holes the device rig turned up are fixed with it, and both defeated the cache outright: `_bootstrap` read `apiConfigProvider` **once** and gave up when it was null — and this repository is built at app root (the locale notifier reads `serviceTerm`), *before* the paired address is off prefs, so `GET /venue/settings` was never issued at all and a handset could run for weeks on a shape cached before a module was bought; it now waits for the address. And the WS listener handled only `venueSettingsUpdated`, which is an **edit** broadcast and not a resync, so a client that cold-booted dark stayed on its cache after the socket returned; it now refetches on `connected` like every other collection (ADR-0021). No offline money risk — `recomputeBill` reads no venue settings, tax and service ride the bill payload.

- **Attribution rides the receipt, and the remainder is the owner's** (ADR-0118). `memberSplit` is the third **mode** key in `venueModeKeys` / `MODE_MODULES` — fail-closed like the other two, and ANDed with the `members` module *and* `membersEnabled` in **one** place per side: `MemberConfig.splitEnabled` server-side, `memberSplitOn` on `VenueSettingsModules` client-side, which is also what `Bill.splitEnabled` carries to the floor. The grain is the **receipt** (`receipts.memberId`), not the ticket line: `visits.memberId` survives as the [[Pemilik tagihan]], and money no share claims is theirs — `pointsBaseByMember` states that as a *subtraction*, which is what makes the remainder impossible to lose. An earn is **one row per member, not per receipt** (a guest with two slips ate one meal), so `reverseEarnForVisit` and `reverseRedeemForVisit` **loop every live row**; a singular `_earnRowFor`-style lookup leaves three of four guests paid after a reopen. Points split across amount receipts but **stempel does not** — a share with no lines has nothing to count. Give-backs moved to receipt scope: `idx_discounts_order_uniq` is now `(receipt_id, source)`, so a share can hold a manual discount, the member's tier discount and a redemption at once — anything printing "the order discount" must sum all three or the slip will not reach its own total. The gate is on the **write and the picker, never a read**: `punchStatus` and `memberReportSection` are deliberately ungated, because switching the mode off **freezes rather than deletes** and a closed month must keep its numbers.

- **A venue may call a table a service, and the word is a locale** (ADR-0127). `serviceTerm` is the fourth **mode** key in `venueModeKeys` / `MODE_MODULES` — fail-closed like the rest, independent of `counterService` — and the one that **gates nothing and branches no writer**: the floor, zones, capacity, locks and moves stay exactly as they were. The word is resolved the way ADR-0083 already resolves words, by picking a locale: `Locale('id','SV')` / `Locale('en','SV')` load `app_id_SV.arb` / `app_en_SV.arb`, which **override only the ~120 strings naming a table and inherit the other ~3900**. `SV` is not a country — it borrows the region slot as a variant marker, which is safe only because nothing here resolves a locale from the platform. Read in **one** place, `SatLocaleNotifier` (via `VenueSettingsModules.serviceTerm`); `MaterialApp`, the process-wide `satL10n`, the ESC/POS struk and the CSV/PDF exporters all follow for free, and a screen that asks about `serviceTerm` for itself is a review finding — that is a copy branch, and copy lives in the ARB. Inheritance is **silent**, so `arb_parity_test.dart` carries the guard: a template value matching `\bmeja\b` (ICU spans masked, or the placeholder named `table` reads as the word) with no override fails CI. The service **charge** was renamed unconditionally to **Biaya layanan · Service charge** in *every* venue — leaving it would print `Layanan 7 · … · Layanan 10%` on one struk. The guest page is outside gen-l10n and picks its noun from a `serviceTerm` flag on `/guest/venue`.

- **Membership is on for a new venue, and switchable off** (ADR-0091, default flipped Aug 2026 — the column default paints a fresh row only, so an existing venue keeps its stored choice). `venue_settings.membersEnabled` gates *every* member route with a 404 — not a 403 — so a client cannot tell an unlicensed venue from an old server, and `MembersRepository` reads that 404 as `enabled: false` rather than an error. The two programs underneath (`memberPointsEnabled`, `memberPunchEnabled`) toggle independently; the till panel and the printed slip both check them before drawing a thing.
- **Lines divide the way money does, and there is one function that does it** (ADR-0119). `memberUnitsOf` (`lib/server/members.dart`) is **the** line-attribution rule of ADR-0118: units on a receipt naming somebody are that [[Pemilik struk]]'s, units on an unnamed receipt or on no receipt at all are the [[Pemilik tagihan]]'s — every unit of an [[Amount receipt]] included, since those own no lines. `punchStatus` (stempel) and `memberHistory` (the Laporan pelanggan product rollup) both read it; a second copy of the subtraction is how one screen says a guest ate three plates and the next says four. It returns **units and leaves voids in**, because a comp is a reward to stempel and not a purchase to the rollup — the caller decides. Ungated on `memberSplit`, same as everything else on the read side. The money half of the same rule is `pointsBaseByMember`.
- **`memberReportSection` no longer walks the window itself.** `memberWindowTrade` / `memberWindowPoints` do, and both the venue block and `memberTradeReport` read them — the report route walks once and hands the scans over. Its wire shape is unchanged; adding a figure means adding it to the scan, not to a second loop. `reportWindow` (was `_windowFor` in `reports_routes.dart`) is public for the same reason: two reports must agree about where a business day ends. `range=all` is resolved **only** in `members_routes.dart` and deliberately not in that shared resolver — `/reports` renders `ReportRange.values` straight, and an unbounded window on a per-bill payload is exactly what its 92-day cap exists to prevent.
- **A bill discount has a `source`** (ADR-0094): `manual` | `member` | `redeem`, one slot each, enforced by the `idx_discounts_bill_source_uniq` partial index. They stack by design — a cashier's promo, the member's standing discount and a points redemption are three different give-backs, and putting them in one slot is how one silently erases another. Everything is frozen at the first payment (ADR-0068), which is why `MemberPanel` gates on `billClosedAt == null && paidAmount == 0` instead of letting a button 409.
- **A new `Capability` reaches existing venues only because the admin role is reconciled on boot.** `_ensureAdminRole` (`lib/server/db/seed.dart`) rewrites `role-admin` to `Capability.values` every Server boot, because that role *is* all capabilities by definition and the Staf sheet shows it read-only — a stored snapshot is the one set nobody can repair. Every other role stores its own set, so a capability a non-admin role needs must be added to `seed_data.dart` **and** granted on already-seeded venues through the role sheet; there is no backfill but the one-off `_ensureWaiterCanVoid` pattern.
- **An offline *settlement* is a journal, not an intent** (ADR-0123). A client-mode `/kasir` loses the host the way a handset does, so the whole settlement surface is capturable — but a settlement is a **chain** (each act reads what the last one wrote) and it is **read** as well as drained, which is why it lives in a client Drift DB (`lib/data/db/`, ADR-0124) rather than the prefs blob the [[Antrean kirim]] uses. Four rules carry it. **One money function**: `recomputeBill` (`lib/domain/use_cases/bill_recompute.dart`) is pure and *both* sides call it — the server's `_recompute` is now only the persistence half, and `settlement_projection.dart` may move parts around but must never compute money; `test/settlement_offline_parity_test.dart` runs one event sequence through the routes and through the projection and compares. **Ids are client-minted, online too** — receipt, payment, discount and refund — and double as the idempotency key; the acts ids do not cover (`assign`, `split-even`, `delete`, `reopen`) ride the journal event id through `x-idempotency-key`, which `idempotent()` in `lib/server/idempotency.dart` wraps the whole settlement router with. **A visit with a non-empty journal is local-authoritative** until its chain drains, *even after the socket returns* — the test is `journal.isNotEmpty || wsConnState != open`, not the socket alone. **Refuse on contradiction, never on staleness**: a bill that grew while the till was dark settles short and that is a correct bill with an outstanding; a refusal halts *that visit's* chain (a refund whose payment was refused must never land) and surfaces on a blocking `/kasir` sheet, because the cash is already in the drawer. Two acts stay online-only — a manager step-up (a PIN hash is a credential; ADR-0099) and member *lookup* (ADR-0092 makes the phone the identity, so no mirrored directory) — while redeeming an already-attached member's points offline is fine. Settlement events **never expire**; a drain past its own business day is backdated from `capturedAt` and audited as `AuditKind.settlementArrivedLate`. Two islanded tills can both collect the same bill and that is **made loud at drain, not prevented** — a designated-cashier flag would be a lease granted by the host that just vanished (ADR-0116). Orders drain before money on this device.
- **The member directory mirrors to the device, and the copy is a copy** (ADR-0129, amends 0123 for lookup only). ADR-0123's member-lookup bullet is overturned: a [[Salinan pelanggan]] fills ahead of the outage from `GET /members/sync?since=`, lives in the client Drift DB (`CachedMembers`, v3) and answers search + attach while dark. Four rules carry it. **The cursor is a counter, not a clock** — `members.mirror_rev`, sharing one sequence with `member_tombstones.rev`; drift stores a `DateTime` at *second* granularity, so a timestamp cursor silently drops any change landing in the cursor's own second and sorting below it, forever. **`touchMember` is the one stamper**, and every writer that changes what a mirror *shows* calls it: `members.dart`, the [[Piutang]] ledger in `debts.dart`, and the bill close (`touchVisitMembers`) — because `visitCount`, `lifetimeSpend`, `lastVisitAt` and stempel progress are derived from trade, not from the member row. A writer that forgets does not fail; it drops that member out of every device's copy until some unrelated edit moves them. **A departure needs a table**: `deleteMember` and `mergeMembers` both `DELETE FROM members`, so `member_tombstones` is what a dark device learns from, and a merge's row names the survivor. **Masking is per capability, at the route**: `settleBill`/`manageMembers` get the whole record, a `takeOrder`-only device gets a salted `phoneHash` + last four and no note, birthday or address — the salt lives in `flutter_secure_storage`, never in the sqlite file, because an unsalted digest of a phone number is not a mask. `viewReports` does not open the route at all. The switch is `venue_settings.member_mirror_enabled`, defaulting **on**, a plain boolean and deliberately **not** a mode key (a mode key fails closed, ADR-0109, which would disable the mirror on precisely the venue that never phoned home); off answers **404**, like membership itself, and the client wipes its copy. The mirror dies with the **certificate**, not the address (ADR-0128's rule), and never on staff sign-out.
- **An offline enrolment is a journal event, and a duplicate number folds** (ADR-0129). Enrol, attach and detach all ride the [[Antrean setelmen]] — one queue, one drain order — with two adjustments: an enrol has no visit, so it rides `kVenueScopeVisitId`, **drained ahead of every per-visit chain** (an attach naming a member the host has never heard of must land second); and **member-scope events confer no local authority** (`SettlementEventKind.isMemberScope`), or a pelayan tagging a regular at order time would make that [[Visit]] [[Kunjungan otoritatif-lokal]] on *their* handset and turn ADR-0116's two-islanded-devices case into the norm. A redemption is **not** member-scope — it takes money off the bill. The id is client-minted and doubles as the idempotency key; when the number is already in the directory the host **folds** into the standing record (`enrolCapturedMember`), answers with the winning id, and the device runs `rewriteMemberId` over everything queued behind it. A fold audits as `memberEnrolFoldedAtDrain` and never as `memberMerged` — that kind means a human chose to merge. An **online** enrol still refuses `phone_taken` so the till can offer the standing record; folding is switched on by the request carrying both `id` and `capturedAt`, which is what an offline capture looks like. Debt writes and manager step-up stay online-only; poin, stempel and [[Piutang]] render with the timestamp they were true at.
- **A visit expense is revenue, and it is not the petty cash box** (ADR-0130). A [[Waiter|pelayan]] may spend cash on the party they are serving — tissues, a complimentary something — and it is recorded as a **[[Pengeluaran kunjungan]]** against the [[Visit]], never as a `cash_entries` row. The box is a standing float that is deliberately *not* revenue (ADR-0089); this comes out of what one visit rang up and **is** revenue-affecting, so the two ledgers never meet and neither appears in the other's report section. `lib/server/visit_expenses.dart` is the fifth writer of the `cash.dart` family and holds two invariants: **the cap** (a visit's expenses may not exceed its subtotal of sent, non-voided lines — pre-tax, pre-discount, binding the *running sum*, re-read inside `db.transaction` per ADR-0100) and **append-only** (no update path, no delete path — not "not yet"; the cash already left). The cap is checked **at capture only**: a void that lands afterwards leaves the expense standing. **The guest pays in full** — the bill total, its receipts and its outstanding never learn an expense happened, and `recomputeBill` is untouched, which is what keeps an expense (a cost absorbed) distinguishable from a [[Diskon (discount)]] (a give-back). `netTotal` and `settledTotal` keep ADR-0039's frozen formulas; the new `TableSessions.expenseAmount` is a column of its own and the subtraction happens once, in the report, as `netAfterExpense`. `settledTotal`'s docstring now says *money billed and settled* — cash in hand is that minus `expenseAmount`. Gated by the mode key **`tableExpense`** (fail-closed, ANDed with `venue_settings.table_expense_enabled` in one place per side — `visitExpenseEnabled` server-side, `tableExpenseOn` on `VenueSettingsModules` client-side), 404 when off. Its own capability `recordTableExpense`, granted to the seeded waiter separately from `takeOrder`; **no manager step-up**, because approval is unobtainable offline (ADR-0099) and a waiter who cannot file it records nothing. A **photo is mandatory**, server-side as well as in the sheet. Categories are **venue-authored** (`visit_expense_categories`, shaped like `DiscountPresets`) and **soft-deleted only** — a removed one orphans a closed month's rows; the catalogue is cached and **warmed at `AppShell`**, the bug ADR-0128 records against the discount presets. Offline it is a `SendIntentKind.tableExpense` **intent**, not a journal event, with two departures from every other intent: its photo lives in the client Drift DB (`QueuedPhotos`, v4) because the queue is a prefs blob, and it **does not expire** at the business-day rollover (`intentExpires`) — an order nobody wants this morning is right to drop, money already spent is not. Its 400 cap refusal and its 403 both **drop rather than stall** the drain, `voidTicket`'s posture. Reached from the **visit**, never the table tile — table detail's context sheet and the `/kasir` bill overlay — so a [[Kedai]] venue with `menuHome` on still has it.
- **A venue keeps more than one tin, and each answers for itself** (ADR-0131, amends 0088/0089). `cash_boxes` is a venue-authored catalogue shaped like `VisitExpenseCategories`; `cash_entries.box_id` is NOT NULL defaulting to `box-main` ("Kas Utama"), seeded on create, on the v73 upgrade **and** on every Server boot. A **balance is per box** — `cashBalance(db, boxId:)` — and ADR-0088's refusal reads that box alone inside the transaction; the venue-wide arm exists for the report's totals and **no guard may use it**. A **transfer is two ordinary rows**, not a fifth `CashEntryKind`: an `expense` out and a `topUp` in, linked by `transfer_peer_id`, written together by `transferCash`, categoryless (nothing was bought), audited **once**, and gated on `editSettings` because funding a tin is not spending from one. `reverseCash` follows that link and undoes **both legs** — half a transfer would leave money standing in a tin it never reached. Retiring a box is refused at a non-zero balance (`box_not_empty`) and there is **no delete**: a closed month must still name where its money came from. Every venue figure in the Kas report is the **sum of `byBox`**, which is what makes a transfer net out with no exclusion rule, while `byCategory` stays venue-wide. Authority is venue-wide (no per-box ACL) and there is deliberately **no module or mode key** — one box is the degenerate case of N, and a fail-closed key would hide an existing venue's box. The audit params gained `{box}` on all four movement kinds and the v73 branch backfills it into existing rows, because `auditText` renders a missing param as `''`. Client-side nothing is cached (ADR-0128 does not apply: `/kas` is tablet-only, admin, no offline path) and the WS frame carries **one box's** balance, so the client re-sums the total — which is what makes a transfer's two frames correct in either order. The selector, the transfer action and the report's per-box block all hide below two boxes. The day ritual funds and counts the **first active box** only, as it always did.
- **A hub is a catalogue, not an authority** (ADR-0134). `/venue` no longer costs `manageStaff`: `capabilitiesFor('/venue')` returns `venueHubCapabilities`, the **union** of its children's gates, derived from `venueHubRoutes` — which comes off the hub's own tile list, so adding a tile widens the hub's gate in the same edit and a second tile→capability table never exists. Tiles filter through `canOpenRoute`, the redirect's own predicate, so a visible tile can never land on `/forbidden`; a missing **capability hides** a tile where an unentitled **[[Modul]] only greys** it (CONTEXT.md §Modul — the buyer is who an upsell is for). `null` reads as ungated on both sides, and `test/venue_hub_gate_test.dart` is what keeps a hub route from ever being null. **`/stock` is now a nav destination** (rail + phone bar, either stock authority, `showStock`), so it is in `_railRoutes`, lights its own slot and carries a one-segment crumb — its `venueHubCrumb` entry is gone, and it keeps its hub tile (unlike ADR-0106's queue, because stock *is* an owner's business). No badge: a low-stock count never clears, and a badge that never clears is a badge nobody reads. The rail's Venue slot and the server-mode sign-in landing both ask the same union, so a waiter no longer meets a slot that only refuses, nor lands on `/forbidden` after a successful sign-in. Phone reaches the hub from `/me`. A **new top-level destination still needs its `_railRoutes` entry** or it reads as Venue.
- **An offline write is an intent, not a row** (ADR-0090). `submitOrder` and `seat` fall back to `sendQueueProvider` when `wsConnStateProvider != open` (or when the request never lands), and the backlog replays through the *ordinary* routes on the next `connected` event. A new offline-capable action means a `SendIntentKind` + an arm in `apiIntentSender` — never a bulk endpoint, or the stock, visit and audit rules gain a second place to drift. `sendQueueDrainProvider` only subscribes because `AppShell` watches it. **A repository's `_resync` guard coalesces, it never drops** (ADR-0116): the reconnect resync and the drain fire off the same `connected` event, so the drain's re-pull always arrives mid-flight, and a dropped one lets the pre-drain response clobber the WS deltas the replay already applied — the board then shows the world as it was a moment before the backlog landed.
- **A void's reason is a code; free text is only for `other`** (ADR-0114, amends 0006). `POST /tickets/<id>/transition → voided` requires a non-empty `voidReasonCode` and requires `voidReason` text **only** when that code is `other`. Demanding text for every code is how four of the five reasons the picker offers answered `400 reason_required` for months: ADR-0006's guard was written when the client still sent the reason's *label*, ADR-0085 stopped it sending one, and nothing revisited the server. `_emitVoidAudit` already falls back to the code's canonical label, so an empty text loses no word. A void is also the **one** ticket transition with an offline path (`SendIntentKind.voidTicket`) — a queued `prep` would replay a kitchen fact that stopped being true, and a queued void is the one intent whose failure leaves a line *live* on the guest's bill. Its 403 is a business refusal that must **not** stall the drain, unlike every other intent's.
- **A ledger guard only holds inside a transaction** (ADR-0100). `spendCash`, `countCash`, `reverseCash`, `spendPoints` and `earnPointsForVisit` re-read the balance (or the existence check) *inside* `db.transaction`, because the balance is derived — `SUM(delta)`, never stored — so no `CHECK` constraint can hold the invariant and the guard lives entirely in Dart. A new ledger writer that skips the transaction is a review finding. The same rule pairs a ledger row with the bill discount it pays for, in `settlement_routes`.
- **Every route factory takes a non-null `ServerAuth`** (ADR-0102). There is no "no auth configured" path that waves a caller through — that branch existed in sixteen files, three of which handed the anonymous caller `Capability.values`. A route test signs in through `test/support/route_auth.dart` and puts the bearer on the request, like a client would.
- **`submitOrder` writes; it does not tell anyone.** The fan-out a written order owes the room — `ticketCreated` per line, `tableUpdated`, `syncVisitMoney`, the stock-flip `menuUpdated` — lives in `broadcastSubmitted` (`lib/server/routes/tickets_routes.dart`), which both `POST /orders` and `acceptGuestOrder` call. A new caller of `submitOrder` that skips it leaves the ticket in the DB and on nobody's screen; that is exactly how the guest-accept path shipped its first device run with an empty KDS.
- **The guest plane is a second, cleartext socket on :8080, and it binds only while the flag is on** (ADR-0105). `venue_settings.guest_ordering_enabled` off means the socket does not exist, not that it answers 403. Toggling it goes through the ordinary server restart, because the router is built once at boot — so a freshly toggled venue serves nothing until a hot **restart**. Nothing on that plane takes a bearer, and nothing staff-facing is mounted on it; `test/guest_plane_test.dart` asks the socket rather than trusting the claim.
- **The guest page is Indonesian and outside the ARB pipeline.** `assets/guest_web/index.html` is one hand-rolled file with its own copy and its own error-code map (ADR-0105). It is the only user-facing surface in this app that `flutter gen-l10n` never sees — a new server error code the page can receive needs an entry in that map or it renders as a bare code.
- **`menu_items.alcohol` is a prompt to a person, not a control.** It badges the [[Menu tamu]] row and warns on the queue card so whoever holds the accept button knows to check an ID; it never hides the item or refuses the order. Written **only** by `PATCH /selforder/items/<id>` — the Menu tamu tab on `/selforder-admin` is the one screen that shows it, so it is the one route that sets it. Deliberately **not** backfilled by category on upgrade (v57 defaults every existing row to false): category names are venue-authored, and guessing which of them mean alcohol is how a soft drink acquires an age check. The seed marks its own three drink categories because it owns them.
- **`guest_stock_override` reaches the client already expired.** `guestMenuJson` emits the *effective* value, not the stored one — a force whose `guest_override_at` predates the current business day arrives as `auto`. The Menu tamu tab's three-way control binds straight to that field, so nothing client-side recomputes the expiry and no button can render held-down after the server has let go. Tapping the selected force clears it to `auto`; without that the only way back to the inventory is to wait for midnight.
- **`guestOrderJson` has a `staffView` flag, and the guest plane must never pass it.** It gates `tableLabel` and `decidedBy` — the guest is told what happened to their order, never by whom. Both planes share one builder on purpose; the flag is what `test/self_order_routes_test.dart` pins.
- **`guest_orders.status` and `menu_items.guest_stock_override` names are persisted** (`pending|accepted|rejected|cancelled`, `auto|forceIn|forceOut`), same rule as `AuditKind` and friends. A `guest_stock_override` is also *expiring*: it is only honoured while `guest_override_at` is at or after the current business day's start, so a manual "habis" call does not outlive the shift that made it. The reject reason is a **code** (`out_of_stock|menu_changed|closed|other`) written to `reject_reason_code` and spelled the same way in the guest page's map — renaming one means renaming both.
- **A table's `guest_code` is minted, never rotated, by anything that runs twice.** `mintMissingGuestCodes` fills blanks only and is what the seed and table-create call; `rotateGuestCodes` kills every printed QR in the venue and is an audited, deliberate act. Putting a fresh code in an `insertOnConflictUpdate` companion is how a re-seed silently invalidates a wall of laminated cards.
- **A plain release is now reachable, and every device installs it** (ADR-0130, amended by ADR-0131). `verdictFor` has a fourth arm — `available`, meaning `installed < latest` with no floor crossed — and it is the fleet's *normal* case: `/push-deploy` defaults to a plain tag, which moves `latest` alone, and for eight releases nothing read `latest`, so no device ever drew the banner or the block. `available` is a **pull, never a push**: it renders only on the `/me` version line, which is a control under `editSettings` and **locked state — never a refused tap — without it**. The `recommended` banner is still `recommended` and still Main-Device-only; it is the one update surface that interrupts. Install itself is **ungated on the block screen** (a device below `min` is out of service and unblocking it is never wrong) and `editSettings` everywhere else. All three surfaces go through `startUpdate` in `lib/ui/core/widgets/update_action.dart` — never `downloadAndInstall` directly — because a **host install stops the embedded server**, and that warning (live-table count, then proceed, mirroring ADR-0015's logout) must not be forgettable per call site. The host also serves a **[[Salinan APK]]**: `lib/server/update_mirror.dart` prefetches the release the moment the gate's `latest` passes the host's own version, into the **application support dir** (not the cache — Android evicts caches, and the mirror exists for the uplink outage that is the whole reason to hold it), one file at a time, `.part` then rename. `GET /update/apk?v=<semver>` serves it and **404s any other version** so the client falls back to GitHub; the route is **unauthenticated, in the middleware skip set beside `/healthz`** (the body is a byte-identical copy of a public GitHub artefact) and is deliberately **not** mounted on the guest plane. No hash check — Android refuses an APK signed by a different key over an installed package, and that is the actual protection. **Android never reports the install back**: `OpenFilex.open` returns `done` when the *intent* launches, so a declined permission, a tapped Cancel and a signature refusal are all indistinguishable from success. The way out is the lifecycle, not a result code — `AppUpdateService` resets `UpdateOpening` to idle on resume, because a successful install replaces this process and there is nobody left to resume. Without it the retry guard leaves the button dead until the app restarts.
- **Release builds run R8** (`isMinifyEnabled` + `isShrinkResources`). Dart is AOT and untouched, but a new plugin that resolves Java/Kotlin classes reflectively needs a keep rule in `android/app/proguard-rules.pro` or it fails only in release. `flutter build apk --release` is the check; debug will not catch it. Crashlytics' Gradle plugin uploads the mapping file, so minified traces stay symbolicated.
- **A sign-in returns an `AdmissionOutcome`, and nothing else** (ADR-0098). The sealed type in `lib/domain/models/admission.dart` is the *only* channel — `AuthState.error`, a `hostOccupied` flag and a `bool` return were the three that preceded it. A new outcome means a subclass **and** an arm in the exhaustive `switch` in `lib/core/localization/admission_text.dart` (which is why the analyzer will tell you), plus an ARB entry in both locales. The outcome carries a code, never a sentence. Admin sign-in has **no offline path** (ADR-0099); a session *restore* does, and the two are deliberately different.
- **`Sp` stops at 48; `SatSize` (`design/layout.dart`) is where a bigger number gets a name.** A panel width, its own inset, a control height. `EdgeInsets.fromLTRB` is now ratcheted by `design_tokens_test.dart` at a frozen baseline — the `no raw spacing literal` ban next to it lists `all`/`symmetric`/`only` only, which is how the sign-in screen stayed green while every inset on it was a literal.
- **The shell publishes its bottom chrome; nothing re-derives it** (ADR-0117). The phone shell floats its tab bar *over* the page (a `Stack`, not a `bottomNavigationBar`), so a vertical scroll view on a shell route must end above it. `AppShell` wraps its child in `ShellInset` (`design/shell_inset.dart`) carrying `_tabBarGap + _tabBarHeight`, and a screen reads `context.shellInset` — **0** where there is no bar: the tablet shell, and every root-navigator push. The old `SatLayout.bottomInset` is **gone**, because it was computed from `MediaQuery` and could therefore only answer "am I a phone": `MenuScreen` and `ReviewScreen` are mounted *both* inside the shell (`/counter`) and pushed outside it (`/table/:id/menu`, `/order/new`, `/takeaway/:visitId/menu`), and no size-derived token can tell those two mounts apart. A screen's **own** floating footer is a separate number that stacks on top (`_cartFooterClearance`, `_sendBarClearance`, `_actionStackClearance`) — `shellInset` clears the bar, the constant clears the footer. `AdminPage` (`admin/_common.dart`) pays it once for nine admin screens. `test/shell_inset_test.dart` holds the list of files mounted inside `ShellRoute`, asserts the list still matches `app_router.dart`, and fails any listed file that builds a vertical scroll view without mentioning `shellInset` — a **new shell route must be added to that list**. A screen whose only scroll views live in sheets (which cover the bar rather than hide under it) opts out with a `// no-shell-inset:` comment naming the reason.

## Design Context

> Guides every UI decision. Tokens live in `lib/ui/core/design/`; this section is the *why*.

### Users

Four staff roles on shared Android hardware:

- **Waiter** — phone, one-handed, walking, tray in the other hand. Glances for half a second between tables. The busiest, least forgiving context.
- **Kitchen** — tablet KDS on a hot line, read from 1–2 m, often through steam, frequently never touched. Read-at-distance beats touch density.
- **Cashier** — settling, splitting, capturing payment proof. Accuracy over speed; money is on the line.
- **Owner / admin** — menu, staff, reports, inventory. Lower frequency, higher complexity tolerance. Seated, not rushed.

Job to be done: get an order from a guest's mouth into the kitchen, correctly, in seconds, without the internet. Everything else is bookkeeping around that.

The app ships **Indonesian and English** (ADR-0083). Indonesian is the hard default — the system locale is never consulted — and the picker is device-local, on `/me` beside the theme sheet.

Copy lives in `lib/l10n/app_id.arb` + `app_en.arb`, generated by `flutter gen-l10n` into `lib/l10n/app_localizations.dart` (class `AppL10n`, committed, analyzer-excluded). `AppStrings` is gone.

- **Widgets:** `context.l10n.foo` (extension in `lib/core/localization/locale_view_model.dart`).
- **No `BuildContext`** — exporters, `auth_error.dart`, pure view-model functions: `ref.read(l10nProvider)`, or take an `AppL10n` parameter.
- **A code crosses a layer, never a sentence** (ADR-0085). Enums carry their key and nothing else (`Capability`, `TicketStatus`, `ReservationStatus`, `StockReason`, `UserRole`, `AlertSoundPreset`); the server sends `kind` / `key` / `code` + params; `StaffException` and the report DTOs carry codes. The words are composed at read time by the resolvers in `lib/core/localization/` — `labels.dart` (enums, capabilities, staff errors, alert sounds), `report_copy.dart` (server-emitted report + void-reason codes), `audit_text.dart` (audit rows). Every resolver falls through to the raw code, so an older row or a newer server never renders blank.
- **Never hardcode user-facing text.** Three bans in `design_tokens_test.dart`, all at zero: copy in a `Text()`, copy in a named param (`label:`, `title:`, `hint:`…), and *any* Indonesian word in a Dart literal under `lib/ui` or `lib/domain` — the last one is what catches a switch arm, a preset list or a `return`. `arb_parity_test.dart` fails on a key, placeholder or plural present in one locale and not the other, because gen-l10n only *warns*.
- Indonesian remains the source language: `app_id.arb` is the template, and new copy is authored there first.

**Not localised, on purpose:** money (`formatIDR`, `groupRupiah` and the rupiah input mask stay `id_ID` in both languages — ADR-0084); the six theme names; venue-authored content (menu items, zones, notes, seed data). Dates *are* localised, so `format.dart` is deliberately half-pinned — see ADR-0084 before "fixing" it.

Domain vocabulary is canonical in `CONTEXT.md`: each term entry carries an `ID · EN` line, and no ARB value may render a domain term any other way (`opname` → Stocktake, not Inspection; `resep` → Recipe, not Prescription).

### Brand Personality

**Sharp, warm, dependable.** Tool-like precision, softened. Amber `#FF9233` on charcoal is the whole thesis: an instrument panel that doesn't feel cold, in a business that is fundamentally about hospitality.

Voice: direct, unfussy, Indonesian-plain. State what happened, not how the system feels about it. No exclamation marks, no apology copy, no personality in error states — a waiter mid-rush needs the fact and the next action.

Emotional goals, in order:

1. **Fast + in control** — every tap resolves visibly. Never ambiguous whether an order was sent.
2. **Calm under chaos** — the screen stays quiet while the room is loud. Nothing shouts unless it genuinely must (`urgent` is a scarce resource).
3. **Effortless / low-thought** — muscle memory. A new hire is productive on shift one, untrained.

### Aesthetic Direction

**The app boots on Neon Terang** — the light Glow palette, bone `#EEEFE0` ground (ADR-0057). Neither brightness is the exception: restaurants run dim and a dark theme is one tap away for the rooms that need it, while terrace and daylight service must survive glare. Both directions ship with genuine high contrast, never washed-out grays. Neon Terang is the roster's most accessible light palette — its semantic hues are authored as ink on white rather than reused from the charcoal ramp.

Color is signal, never decoration. The neutral ramp (`bg0`–`bg4`, `border0`–`border2`, `textHi`→`textDim`) carries structure; semantic tokens (`accent`, `success`, `warn`, `urgent`, `info`, `violet`) carry meaning only. Course colors (`cDrinks`/`cStarters`/`cMains`/`cDesserts`/`cFire`) alias the semantic set deliberately — one hue vocabulary, learned once.

Motion is welcome but purposeful: `satEaseOut`, transform + opacity only, always collapsing to a static final state under reduced motion (`motionEnabled(context)`). Motion clarifies what changed; it never entertains and never costs a waiter time.

**Anti-references — explicitly not this:**

- **Legacy Windows POS.** Gray gradients, beveled buttons, 6pt dense grids, 2005 enterprise chrome. This is the thing being replaced; resembling it is failure.
- **Generic Material 3 default.** No purple seed, no stock M3 look. `useMaterial3: true` is a substrate, overridden by `SatColors` + `SatType`. If a screen could be any Flutter demo, it's wrong.
- **Consumer food-delivery app.** No hero photography, gradients, promo banners, or gamification. Staff tools, not a storefront.

### Design Principles

1. **Glanceable beats dense.** Optimize for the half-second look from arm's length. Tap targets sized for a moving thumb; KDS text sized for 2 m. When density and legibility conflict, legibility wins.
2. **Color is signal, not decoration.** Reach for the neutral ramp first. `urgent` earns its red by being rare — if everything is urgent, nothing is.
3. **State must be unambiguous.** Sent vs. unsent, locked vs. free, ready vs. pending, settled vs. open — never inferable only from subtle color. Pair every state with text, shape, or position.
4. **Both themes, both real.** Every surface ships dark and light with genuine contrast. Never hardcode a `Color` — go through `context.sat`.
5. **Quiet motion, honest feedback.** Every action produces immediate visible acknowledgement; no animation delays a confirmation. Reduced motion always yields the final state instantly.
6. **Degrade loudly, fail safely.** Offline, mid-reconnect, and stale-cache states are first-class UI — this app's whole promise is working when the network doesn't.
